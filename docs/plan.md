# Sentwise — project plan (replan toward the first paid subscription)

**Status:** draft updated 2026-10-28, awaiting Michael's approval of M6 (approval = merging `plan/sign-in-first`). **Pipeline item:** sentwise#31. **Planner branch:** `plan/sign-in-first`. The previously approved M1–M5 plan remains unchanged.

## Problem and users
Account Executives lose 30+ minutes a day writing post-call follow-ups and replies. Sentwise is a native macOS menu-bar app that learns the user's voice from their own Sent mail and drafts the follow-up email from a call transcript (and replies to reply-worthy mail), which the user reviews and approves in the app. No bot joins the call; mail, voice profile and transcripts stay on the Mac; drafting goes through Sentwise's stateless managed proxy, which does not log or retain request or response bodies.

- **Primary user:** "Marcus", an AE with 4–8 calls a day on a company MacBook, corporate Gmail on a Google Workspace domain, who expenses $15–20/month tools without asking.
- **Secondary:** "Priya", a technical professional who lives in email and wants drafts waiting.
- **How we know it worked (company goal):** first, one paid subscription from someone who is not Michael; then MRR covering fixed costs (Apple Developer, domains, two Workspaces, hosting, inference). The weekly measure is visitors → downloads → trials → checkouts opened → paid, by tier.

## Architecture and stack (unchanged)

- **Service:** Cloudflare Worker `sentwise-service` (TypeScript, Vitest, Wrangler), Clerk production instance, Paddle Billing live, Workers Analytics Engine for aggregate, pseudonymized metrics. Production deploys are Michael's.
- **Site:** Next.js 16 on Vercel (`sentwise-landing-page`), MDX wired but unused.
- **QA:** Lucius on the Agent Mac Mini (Peekaboo, screen recording) for the app; the `uat` agent with Playwright, also on the Mini, for the site and HTTP endpoints. Never the MacBook.
- **No seed database.** M1–M5 fixtures remain in the test-case preamble. M6's external OAuth mailbox names, readiness and deterministic subjects are documented without addresses or credentials in `docs/qa/seed-data.md`.

## Risks
- **The purchase test runs on a separate sandbox deployment (item 123, re-scoped 2026-10-13).** A second Worker, `sentwise-inference-sandbox`, runs the same code configured for the Paddle sandbox and a Clerk development instance, and a "Sentwise QA" build of the app points at it. Production carries no sandbox state, so sandbox prices cannot leak to customers by construction; TC-M3-05 keeps one read-only check that the production build still shows live prices. If the sandbox deployment slips, the fallbacks are a single-use 100%-off live discount code, then a real $9 Starter purchase refunded the same day.
- **The two services must stay in lockstep.** A purchase test on the sandbox only proves production if both Workers run the same code. The two deploy separately: production when Michael runs `wrangler deploy` or approves the gated Deploy workflow, the sandbox when its `deploy-sandbox.yml` job is dispatched. Every sentwise-service revision is deployed to both, the QA build is cut from the release tag it verifies, and `docs/billing-qa.md` records the sandbox's deployed tag. The M3 run report names the sentwise-service commit under test and records both deployed revisions as acceptance evidence: (1) sandbox: the `deploy-sandbox.yml` run id and the commit SHA (and tag) it deployed; (2) production: the latest deployment's version id and created time from `npx wrangler deployments list` for the `sentwise-inference` Worker, plus the Deploy workflow run id and its commit SHA when that deployment came from the workflow (a manual `wrangler deploy` is mapped to its commit by the orchestrator from the deploy log or tag). Both SHAs must equal the commit the report names. If production is on a different commit, M3 is not accepted until production is redeployed at that commit or the run is repeated against the commit production runs. `wrangler deployments list` reads Cloudflare with Michael's login, so the orchestrator runs it, not Lucius. Configuration drift (a secret, a price ID, a binding added to production only) is the remaining gap; every new binding or var goes into both `wrangler` environments in the same change.
- **Two Sentwise apps on the QA Mini.** The QA build has its own bundle identifier, name, status-item label, Keychain service, Application Support directory, defaults suite, and URL scheme (`sentwise-qa://`) so it cannot overwrite production data or catch production sign-in callbacks (TC-M3-11, TC-M4-03) (the 2026-10-11 Keychain incident, item 115); Lucius quits one before driving the other.
- **Clerk may block plus-addressed emails** (a dashboard restriction). The trial fixtures use `luciusfox+trial-<date>@prowlqa.dev`; if blocked, they need the wave-2 test mailbox (Michael's one-time Workspace step, genkei-ops P1-3).
- **Signing the QA Mac into a trial account disturbs Lucius' daily pass.** Every M2/M3 case that switches accounts ends by signing back in as the comped account and deleting the throwaway account.
- **Free Vercel Analytics has no custom events**, so the site funnel stage is page views plus GitHub release download counts, not click-level. Open question 2.
- **Google sign-in depends on an owner dashboard step** (Clerk callback allowlist). If it slips, 121 slips; M4 still ships with 110/105/106.
- **The distribution channel is not chosen yet** (genkei-ops P1-1). M5's demo uses whichever post that plan produces; if none exists by M5, M5 waits, but M1–M4 do not.
- **M6 Google release is externally gated.** The public sign-in-first flag stays off until the landing-page verification work and 120×120 logo are accepted through the Google verification/CASA chain and item 134 is complete. Build and QA can proceed with the QA flag; owner approval flips the public release variable.
- **Microsoft work tenants can block user consent, IMAP or SMTP AUTH (R1).** Probe both protocols at connect, show the approved admin note, and release personal accounts first if work-account verification lags.
- **The Entra loopback assumption must be proved (R2).** Item 136 verifies random-port `http://localhost`; if rejected, use the manifest's `http://127.0.0.1` fallback before exposing the button.
- **Sent copies are assumed server-side (R3).** The live fixture test confirms Sent Items and adds a Microsoft-only APPEND only if the assumption fails.
- **Publisher verification can lag partner enrolment/domain matching (R4).** Personal Microsoft accounts may ship first under the recorded assumption; work-account public claims wait.
- **Microsoft rotates refresh tokens (R5).** Persist every returned refresh token and cover rotation in CI plus TC-M6-05; otherwise a healthy-looking account later breaks.

## Marketing angle
**"Your follow-up is written the moment your call ends — in your voice, from your own mailbox."** For AEs who already run a notetaker: Fathom, Granola and Otter give you a summary stuck in their app and keep your calls in their cloud; Sentwise turns any transcript into a send-ready email that sounds like you, nothing is stored on Sentwise's servers or used for training, and you approve every word. Proof points a writer can use: no bot joins the call, no API keys, 14-day trial with no card, $9/$19/$39 monthly, native Mac app. Do not claim "before you end your call" (item 86 is not built) or model-provider zero retention. The beta story (0.x, built in public, open core) suits founder-led channels: a launch post on sentwise.ai/changelog, LinkedIn (the AE audience lives there), and the sales-community subreddits and Slack groups the distribution plan picks one of. The update email and changelog entries come from each release's CHANGELOG section. M6 adds a conversion proof point without changing the ICP: **“Connect with Google—or Microsoft next—without hunting for an app password; your mail still stays on your Mac.”** Do not claim Outlook/M365 support publicly until the personal-account release passes, or imply that drafting content never leaves the device.
