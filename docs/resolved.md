### ~~77: Watcher IMAP fetch leaks an unfulfilled `EventLoopFuture` (crashes Debug builds)~~
**Resolved**: 2026-08-25 (branch imap-future-leak, commit f386dca)
**Description**: A Debug build crashed with `EXC_BREAKPOINT`/`SIGTRAP` in NIO's debug-only `EventLoopFuture.deinit` assertion during the watcher's periodic fetch. Root cause: `ClientBootstrap.connect(host:port:)` uses **Happy Eyeballs**, so NIO runs the bootstrap's `channelInitializer` once per resolved IPv4/IPv6 candidate; each run created a promise stored in a per-channel tracker, but only the winning channel's future was consumed. A losing candidate that never became active never received `channelInactive`, so its handler never fulfilled its promise, and destroying the tracker's `[ObjectIdentifier: EventLoopFuture<…>]` dictionary deallocated an unfulfilled future (compiled out of Release, but a real resource-management bug that destabilized Debug dogfooding). **Fix:** the nine near-identical per-path `*Attempts` trackers are replaced by one generic `ChannelPromiseTracker<Value>` that guarantees single-completion via an atomic, lock-guarded claim. `register(_:)` hands each channel's handler a completion closure that claims its promise (an entry flag flipped `false`→`true` under the lock) before completing it; `failRemaining(_:)`, run from the provider method's `defer`, fails every still-unclaimed promise. Because the claim is the single lock-guarded ownership transfer, the handler's closure and `failRemaining` are mutually exclusive per promise — so no promise is ever completed twice (NIO traps on double-completion) or left unfulfilled on any path (success, auth failure, connection failure, timeout, or losing Happy-Eyeballs candidates). `future(for:)` peeks rather than removes, so the winner's future stays retrievable and is excluded from `failRemaining` (already claimed by the time the `defer` runs). Handlers now settle through the completion closure instead of holding the `EventLoopPromise` directly. The identical latent leak is fixed the same way across the sibling paths: verify/connection-test, body fetch, header fetch, search, message page, append, bulk cleanup, and SMTP send. **Tests:** new `ChannelPromiseTrackerTests` (7) prove single-completion in both orderings (handler-then-`failRemaining` and `failRemaining`-then-late-handler), idempotent completion, `future(for:)` peek semantics, and a full drain of all promises when no winner is consumed (the connection-failed path); run under Debug, a leaked promise would trip NIO's assertion inside these tests, so a green run proves no leak. SentwiseMail package suite 170 tests green (was 163); the app + `SentwiseTests` target compile and link against the change (`TEST BUILD SUCCEEDED`). Files: new `Packages/SentwiseMail/Sources/SentwiseMail/ChannelPromiseTracker.swift`; updated `IMAPFetch`, `IMAPMailProvider`, `IMAPBodyFetch`, `IMAPHeaderFetch`, `IMAPSearch`, `IMAPMessagePage`, `IMAPAppend`, `IMAPBulkCleanup`(+`Handler`/`Handler+Envelope`), `SMTPSend`; new `ChannelPromiseTrackerTests.swift` plus the eight handler test harnesses and `MailProviderTests` updated for the new completion-closure API.

### ~~27: Resilience: offline queue + retry~~
**Resolved**: 2026-08-06 (branch offline-queue)
**Description**: Network/API/token failures are now handled as a system rather than per draft. A shared `RetryRunner` (bounded exponential backoff — 4 attempts, 1s base, 30s cap, equal jitter, injectable sleep/random seams for deterministic tests) wraps every resilient operation via `AppState.withResilientRetry`: SMTP send, IMAP save-as-draft APPEND, watcher inbox fetches (including catch-up expansion pages), and per-message draft generation (LLM call).
